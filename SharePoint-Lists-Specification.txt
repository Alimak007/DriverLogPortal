PURPOSE
This file is the single checklist of every SharePoint change the solution needs.
It is maintained alongside the code: when a model in src/common/models changes,
this file changes in the same commit.

HOW TO READ IT
  [NO CHANGE]  Touch nothing. Existing process depends on it.
  [MODIFY]     Existing list, add or alter columns. Migration script required.
  [CREATE]     New list, build from scratch.

Internal names are given where they differ from the display name. Create the
column with the internal name FIRST (no spaces), then rename the display name,
otherwise SharePoint bakes a _x0020_ into the internal name forever.

3.1  VehicleMaster                                                      [MODIFY]
--------------------------------------------------------------------------------
PROBLEM TODAY
  Title holds the DRIVER'S NAME, and there is no vehicle type column at all,
  which makes automatic matching impossible.

CHANGE
  Re-key to the number plate and extend. The existing driver-name relationship
  is preserved as a DEFAULT ASSIGNMENT so no current data is lost and pool
  allocation becomes possible.

COLUMNS TO ADD OR ALTER
  Display name   Internal name   Type                      Req  Idx  Note
  -------------  --------------  ------------------------  ---  ---  ------------
  PlateNo        PlateNo         Single line of text       YES  YES  Becomes the
                                                                     Title. The
                                                                     natural key.
                                                                     Enforce
                                                                     unique.
  VehicleType    VehicleType     Lookup -> VehicleTypes     YES  YES  Mandatory
                                 (show field: Title)                  for matching
  Make           Make            Single line of text       no   no   Shown to the
                                                                     requester on
                                                                     confirmation
  Model          Model           Single line of text       no   no   As above
  Colour         Colour          Single line of text       no   no   As above
  Capacity       Capacity        Number (integer, min 1)   no   no   Validated
                                                                     against
                                                                     NoOfPax
  DefaultDriver  DefaultDriver   Lookup -> DriversMaster    no   no   The existing
                                 (show field: DriverName)             Driver Name
                                                                     relationship,
                                                                     now OPTIONAL
  Property       Property        Lookup -> PropertyMaster   no   YES  Scoping
  Status         Status          Choice                    YES  YES  See below

  Status choices (exact strings, do not localise in the list):
      Available | On Trip | Under Maintenance | Retired
      Default  : Available
      WRITER   : Power Automate flows ONLY. Never set from a web part, never
                 set by hand. A nightly reconciliation flow corrects drift.

COLUMNS RETAINED UNTOUCHED (the logbook still joins on them)
      Client, DriverID, UserID, Viewer, Approver, OldUserID

MIGRATION STEPS (reversible)
  1. Export the current list to Excel. Keep the file.
  2. Add a temporary text column OldTitle. Copy Title into it for every row.
     This is what makes the migration reversible.
  3. Create the new columns above (VehicleTypes list must exist first).
  4. Populate PlateNo for every row from the fleet register.
  5. Populate VehicleType for every row. NO ROW MAY BE LEFT BLANK - a vehicle
     with no type can never be matched.
  6. Set DefaultDriver from OldTitle by matching the driver name to the new
     DriversMaster.DriverName. Report every unmatched row for manual fixing.
  7. Set Title = PlateNo for every row.
  8. Set Status = Available for every active vehicle, Retired for the rest.
  9. Verify, then and only then drop OldTitle.
  ROLLBACK: Title = OldTitle, delete the added columns.

--------------------------------------------------------------------------------
PROBLEM TODAY

CHANGE
  Rebuilt as the single canonical driver record.

COLUMNS
  Display name        Internal name       Type                   Req  Idx
  ------------------  ------------------  ---------------------  ---  ---
  DriverName          DriverName          Single line of text    YES  no
                      -> becomes Title
  UserAccount         UserAccount         Person or Group        YES  YES
                                          (People only)
  DriverID            DriverID            Single line of text    no   YES
  Phone               Phone               Single line of text    no   no
  LicenceNumber       LicenceNumber       Single line of text    no   no
  LicenceExpiry       LicenceExpiry       Date only              no   no
  QualifiedVehicle-   QualifiedVehicle-   Lookup -> VehicleTypes no   no
    Types               Types             MULTI-SELECT
  HomeProperty        HomeProperty        Lookup->PropertyMaster no   YES
  Status              Status              Choice                 YES  YES
  MaxConcurrentTrips  MaxConcurrentTrips  Number, default 1      no   no
  IsActive            IsActive            Yes/No, default Yes    no   YES

  Status choices (exact strings):
      Available | On Trip | On Leave | Inactive
      Default  : Available
      WRITER   : Power Automate flows ONLY.

  Column notes
      UserAccount     Identity for login, for targeting offers, and for the
                      Accept check. The Claim flow compares the calling user
                      against THIS column before it writes anything.
      DriverID        Joins to the existing logbook lists. Keep the existing
                      values exactly.
      Phone           PERSONAL DATA. Released to a requester only after that
                      driver has accepted, and only for that trip.
      LicenceNumber   PERSONAL DATA, UAE PDPL. Visible to Fleet Admins ONLY.
      LicenceExpiry   PERSONAL DATA, Fleet Admins only. An expiry that falls
                      inside the trip window EXCLUDES the driver from the
                      broadcast.
      MaxConcurrent-  Cap for the AUTOMATIC engine only. A Coordinator may
        Trips         exceed it manually, with the override recorded on the
                      trip.
      IsActive        Soft delete. Never delete a driver row - the logbook and
                      TripStatusHistory reference it.

MIGRATION STEPS (reversible)
  1. Export the current list. Keep the file.
  2. Add OldTitle, copy Title into it.
  3. Create all columns above.
  4. Set DriverName = OldTitle, then Title = DriverName.
  5. Populate UserAccount for every driver. THIS IS THE BLOCKING STEP - a
     driver with no UserAccount can never be offered a trip or accept one.
     Report every blank before go-live.
  6. Populate DriverID from the existing logbook values so the join holds.
  7. Populate QualifiedVehicleTypes. A driver with none is excluded from
     every broadcast, so treat blank as a data-quality failure, not a default.
  8. Populate LicenceNumber, LicenceExpiry, Phone, HomeProperty from the
     owning team (see OPEN QUESTION: who owns driver master data).
  9. Set MaxConcurrentTrips = 1 and IsActive = Yes for all current drivers.
  ROLLBACK: Title = OldTitle, delete the added columns.

4.5  RideOffers                                                         [CREATE]
--------------------------------------------------------------------------------
PURPOSE  One row per driver per broadcast. This is the complete record of who
         was offered a trip and who declined - what lets you defend an
         allocation in a fairness dispute.
GROWTH   THE FASTEST-GROWING LIST IN THE SOLUTION. One row per eligible driver
         per request. Archive aggressively.

  Display name     Internal name    Type                        Req  Idx
  ---------------  ---------------  --------------------------  ---  ---
  Title            Title            Single line of text         YES  no
  Request          Request          Lookup->TransportRequests   YES  YES
  Driver           Driver           Lookup -> DriversMaster     YES  YES
  Vehicle          Vehicle          Lookup -> VehicleMaster     no   no
  OfferedOn        OfferedOn        Date and Time               YES  YES
  ResponseStatus   ResponseStatus   Choice                      YES  YES
  RejectionReason  RejectionReason  Choice                      no   no
  RejectionNotes   RejectionNotes   Multiple lines, plain       no   no
  RespondedOn      RespondedOn      Date and Time               no   no

  ResponseStatus choices (EXACT):
      Pending | Accepted | Rejected | Expired | Closed | Withdrawn
      Default: Pending
      Pending   - offer is open, window running
      Accepted  - this driver won the race
      Rejected  - driver declined with a reason
      Expired   - window closed with no response
      Closed    - another driver accepted first
      Withdrawn - the Coordinator assigned manually, skipping the broadcast

  RejectionReason choices (EXACT - this is a dropdown for the driver, never
  free text, because it is reported on):
      Already on a trip | Vehicle unavailable | Outside my shift |
      Personal reason | Other
      RejectionNotes is only shown when "Other" is chosen.

  VEHICLE IS USUALLY BLANK AT BROADCAST TIME. The broadcast confirms only that
  a suitable vehicle EXISTS. The vehicle is bound at CLAIM time. Binding a
  vehicle to every offer would reserve the whole fleet against offers that
  will mostly be declined.

  INDEXES: Request, Driver, ResponseStatus, OfferedOn.

SECTION 5 - SHAREPOINT GROUPS AND PERMISSIONS
================================================================================
Five groups. Every rule is enforced HERE or in a flow. A rule that exists only
in the web part is NOT a rule: any user who can read a list can read every item
in it through the REST API regardless of what the interface shows.

  Group            Master data   TransportRequests        RideOffers
  ---------------  ------------  -----------------------  ------------
  FM Requesters    None          Add, read + edit OWN     None
  FM Drivers       Read          Read own property        Read own
  FM Coordinators  Read          Contribute               Read
  FM Admins        Full control  Contribute               Read
  FM Viewers       Read          Read                     Read

  Group            TripAssignments  Reports
  ---------------  ---------------  -------
  FM Requesters    Read own         None
  FM Drivers       Read own         None
  FM Coordinators  Contribute       Read
  FM Admins        Contribute       Read
  FM Viewers       Read             Read

  "Master data" above means: PropertyMaster, DLClientMaster, VehicleMaster,
  DriversMaster, VehicleTypes, Locations, AllocationRules, Templates.

  DRIVERS GET NO DIRECT WRITE PERMISSION ON RideOffers OR TripAssignments.
  "Edit only the trips assigned to me" and "accept only offers made to me"
  cannot be expressed through SharePoint item-level permissions. Driver writes
  therefore go through Power Automate flows running under a SERVICE IDENTITY,
  which verify that the calling user matches DriversMaster.UserAccount on the
  relevant offer or trip BEFORE writing.

  NO GROUP RECEIVES DELETE ON TripStatusHistory OR NotificationLog, INCLUDING
  ADMINS. Both are append-only audit lists.

  Enable SharePoint audit logging on the site. Retention period to be set by
  the compliance team.

  PERSONAL DATA (UAE PDPL)
      DriversMaster.LicenceNumber and .LicenceExpiry  -> Fleet Admins ONLY
      DriversMaster.Phone  -> released to a requester only after that driver
                              accepts, and only for that trip
      The requester's phone -> released to the driver on the same basis
      No personal data in any log. Correlation ID on every write path.

SECTION 6 - INDEXES, VIEWS AND THE 5,000 ITEM THRESHOLD
================================================================================
These four lists WILL pass 5,000 items:
      TransportRequests, RideOffers, TripAssignments, TripStatusHistory
RideOffers grows fastest - one row per eligible driver per request.

BEFORE GO-LIVE
  1. Create every index marked Idx above. Indexes cannot be added once a list
     is over the threshold without a maintenance window.
  2. Filter EVERY default view on an indexed column. An unfiltered view on a
     list over 5,000 items throws, and it throws for everyone at once.
  3. Set page size to 50 on every view and in every service-layer query.
  4. Schedule the monthly archive: completed trips older than 24 months move
     to an archive list. RideOffers rows for closed requests older than 12
     months may be archived earlier.

SERVICE-LAYER RULE
  At most 4 batched REST calls on a dashboard load. Verified by network trace
  at code review.

SECTION 8 - OPEN QUESTIONS THAT CHANGE THIS SPECIFICATION
================================================================================
In the order they block work. Each one is carried from the requirements
document; the answer changes the schema or the build.

  [ ] 1. DO DRIVERS HAVE A MAILBOX?  <-- HIGHEST PRIORITY
         They have accounts but no Teams. Without a mailbox the broadcast
         e-mail cannot be sent and the ONLY route to the driver is the
         dashboard poll. This changes the whole driver-engagement design, not
         just a column.

  [ ] 2. REQUEST ID FORMAT.  FB-0001 or FB-20260925-0001?
         Both appear in the mockups. Implemented as a switch in
         src/common/config/AppConfig.ts, defaulting to FB-0001. Must be
         decided BEFORE the first production request is created - the format
         cannot be changed afterwards without reissuing every identifier.

  [ ] 3. STATUS SET.  Four driver taps (Assigned, En Route, In Transit,
         Completed) are specified and built. If Picked Up and En Route must
         remain SEPARATE chips, that adds a fifth tap and a fifth TripStatus
         choice.

  [ ] 4. WHO OWNS DRIVER MASTER DATA?
         The DriversMaster rebuild needs licence numbers, expiry dates, phone
         numbers and vehicle-type qualifications FOR EVERY DRIVER. HR or the
         fleet team? This blocks migration step 7 and 8, which block the
         broadcast engine entirely.

  [ ] 5. IS PLUMSAIL FORMS THE HOUSE STANDARD?
         DriverLogs carries a Plumsail data table. If Plumsail is standard the
         requester form could be built with it rather than SPFx, which changes
         the build materially.

  [ ] 6. CLIENT AND CLIENT GUEST REQUESTS - does the external client ever log
         in themselves, or does a staff member always raise the request on
         their behalf? External login means additional licensing and a
         different security model.

  [ ] 7. HOW MANY PROPERTIES, and should a Coordinator at one property ever
         see another property's requests?

  [ ] 8. LOCATIONS MASTER - who owns it, how many entries at launch, and may a
         requester propose a new location? (If yes, Locations needs an
         approval column and a proposed-by column.)

  [ ] 9. ARABIC AT LAUNCH OR LATER?
         Right-to-left is inexpensive to design in now and expensive to
         retrofit. The Templates list already carries a Language column for
         this reason.

  [ ] 10. RETENTION for completed trips and for driver personal data.
          Drives the archive schedule in Section 6.

  [ ] 11. VOLUMES - trips per day, number of drivers and vehicles. These drive
          the indexing and threshold strategy and the Power Automate plan.

SECTION 10 - WHAT THE SPFx SOLUTION ASSUMES, AND WHERE IT WILL TELL YOU
================================================================================
The web parts are built against this specification. Where the requirements did
not supply a name, the code makes an assumption and SAYS SO at runtime rather
than failing silently.

  ASSUMED, NEEDS CONFIRMING
    DLClientMaster.Driver and .Property
        The service layer filters on these internal names. If they differ,
        driver property scoping falls back to DriversMaster.HomeProperty and
        writes a console warning naming this file. Confirm before go-live:
        a driver allocated to a second property will otherwise not see that
        property's requests.
    PropertyMaster.Title
        Used for the property name throughout. Confirm.

  WRITTEN BY THE WEB PART (the only direct write in the solution)
    TransportRequests - item creation, then RequestId written back from the
    SharePoint item ID. Everything else goes through a flow.

  READ BUT NEVER WRITTEN BY THE WEB PARTS
    VehicleTypes, Locations, AllocationRules, PropertyMaster, DLClientMaster,
    DriversMaster, VehicleMaster, RideOffers, TripAssignments,
    TripStatusHistory, AvailabilityBlocks

  NEVER READ BY THE BOOKING WEB PART, DELIBERATELY
    VehicleMaster, DriversMaster, AvailabilityBlocks, TripAssignments.
    The requester chooses a vehicle TYPE, never a vehicle, and the booking
    web part does not query availability at all - anything it read would be
    reachable by that user through the REST API regardless of what the
    interface displays.

  FLOW ENDPOINTS THE WEB PARTS CALL
    claim, respondToOffer, updateTripStatus, manualAssign, cancel, reject,
    setEta. Each is a web part property, set per environment. Until one is
    configured, that action fails with a message naming which URL is missing -
    it does not fail silently.

ADDENDUM - ROUTE DISTANCE (15 October 2026)
================================================================================
Added when the booking form started reading a planned road distance from the
Google Routes API, so that drivers are no longer required to key odometer
readings at the kerbside.

TransportRequests  [MODIFY]  - two columns to add

  Internal name              Display name          Type     Required  Indexed
  -------------------------  --------------------  -------  --------  -------
  EstimatedDistanceKm        Estimated distance    Number   no        no
  EstimatedDurationMinutes   Estimated duration    Number   no        no

  EstimatedDistanceKm        One decimal place. Kilometres by road, pickup to
                             drop-off, as the Routes API returned them at the
                             moment of booking.
  EstimatedDurationMinutes   Whole minutes, free-flowing traffic.

  BOTH ARE OPTIONAL AND MUST STAY OPTIONAL. If Google is unreachable, or the
  Routes API is not enabled, the booking still has to succeed - it simply
  saves without an estimate. Marking either column Required would turn a
  third-party outage into an inability to book a car.

WHAT THESE NUMBERS ARE NOT
  They are the PLANNED laden leg only. They do not include the driver's run
  from wherever they are to the pickup point, and they cannot include a
  detour, a diversion or a wrong turn, because they were calculated before the
  trip happened.

  TripAssignments.OpeningReading / ClosingReading still measure the VEHICLE,
  and remain the preferred figure wherever a driver supplies them. They are
  now optional rather than mandatory.

REPORTING RULE
  Trip Summary and Vehicle Utilisation take the odometer delta when both
  readings exist, and fall back to EstimatedDistanceKm when they do not. Trip
  Summary carries a "Distance from" column reading Odometer or Estimated, so
  the two measurements are never silently totalled as one. Vehicle Utilisation
  is an aggregate and cannot carry that label - use Trip Summary when the
  distinction matters, for example a fuel reconciliation.

GOOGLE CLOUD PREREQUISITE
  The Routes API must be enabled on the project behind the key (project
  725881869333 for the interim key). Without it every booking saves with an
  empty estimate and the console logs a 403 naming the disabled API.
  The legacy Directions API is NOT an alternative - Google has closed it to
  projects created from 2025 onwards, which is why this uses Routes.

ADDENDUM UPDATE - ODOMETER BECOMES OPTIONAL (15 October 2026)
--------------------------------------------------------------------------------

TripAssignments  [MODIFY]  - two columns to add

  Internal name              Display name          Type     Required  Indexed
  -------------------------  --------------------  -------  --------  -------
  EstimatedDistanceKm        Estimated distance    Number   no        no
  EstimatedDurationMinutes   Estimated duration    Number   no        no

  Copied from the TransportRequests row when the trip is created - by
  acceptOffer for an automatic allocation, and by manualAssign for a
  Coordinator one. Reassigning an existing trip does not touch them, because
  the route has not changed.

  A SNAPSHOT ON PURPOSE. If someone edits the request afterwards the trip
  keeps the distance that applied when it was allocated, which is what a
  historical trip sheet should show. It also means the monthly TRF can be
  built from TripAssignments alone, with no join back to TransportRequests.

ODOMETER RULE - ALL OR NOTHING

  OpeningReading and ClosingReading stay OPTIONAL columns, but the driver
  form now enforces a pairing:

    Driver taps "On my way"  ->  opening reading OFFERED, may be skipped.
    Driver taps "Complete"   ->  closing reading is HIDDEN if no opening
                                 reading was given;
                                 SHOWN AND MANDATORY if one was.

  The closing reading must also be greater than the opening one.

  A trip therefore ends in exactly one of two states:
    - both readings present  -> distance is MEASURED, and always preferred
    - neither present        -> distance falls back to EstimatedDistanceKm

  There is deliberately no third state. One reading alone cannot be
  subtracted into a distance, and storing it would look like data while being
  useless to the trip sheet.

MONTHLY TRF
  Where a trip has no odometer pair, the TRF uses TripAssignments.
  EstimatedDistanceKm. Trip Summary in the Reports web part shows a
  "Distance from" column reading Odometer or Estimated so the two are never
  silently totalled as one.
